# Deployment

## How publishing works

This repository is served by **GitHub Pages** from the `main` branch. There is no
build step and no deploy workflow: pushing to `main` publishes. Pages usually
reflects a push within a minute.

That has a consequence worth stating plainly: **a push to `main` is a release.**
It reaches every device with the app installed on that device's next launch.
There is no staging environment. Work on a branch, open a pull request, and merge
when you mean to ship.

## Releasing a change

1. **Rebuild the shell from source.** The application source is `apps/privee` in
   the [`privee`](https://github.com/mish5000/privee) repository. Do not
   hand-edit `index.html` here — the next rebuild silently discards the edit.
2. **Bump the build number.** `version.json` carries `v` (integer, monotonic) and
   `build` (human-readable date). The running app polls this file to notice a
   newer deploy, so a shell change shipped without a bump will not prompt anyone
   to reload. The source of truth is `apps/privee/build.txt`, mirrored here.
3. **Commit the artifact.** One intent per commit. Data-only refreshes should be
   their own commits, separate from shell changes.
4. **Push and verify.** Do not assume the deploy landed — check it.

## Verifying a deploy actually went live

Pages serves from a CDN, so a green push is not evidence. Confirm the new build
number is being served:

```sh
curl -s "https://mish5000.github.io/maison-x9k2m7q4/version.json?ts=$(date +%s)"
```

The `v` in the response must match the build you just pushed. If it does not, the
CDN has not picked it up yet — wait and re-run rather than pushing again.

Then confirm the shell itself changed, not just the sidecar:

```sh
curl -sI "https://mish5000.github.io/maison-x9k2m7q4/index.html" | grep -i etag
```

## Rolling back

Because the deployed artifact is committed verbatim, rollback is a revert — there
is nothing to rebuild:

```sh
git revert <bad-commit>
git push origin main
```

Then re-run the verification curl above. If a bad service worker is the problem
rather than a bad shell, reverting `sw.js` is not always enough: clients already
holding it need the `CACHE` constant bumped so the `activate` handler purges the
old cache. The app also accepts a `flush` `postMessage`, which deletes the cache
outright.

## Data refreshes

`dishes.json` and `lineups.json` are regenerated by the pipeline in
the `privee` repository (`curation/` and `scripts/lineups/`) and committed here. They
are served network-first, so a refresh reaches clients on their next launch
without touching the shell or `version.json`.

Never hand-edit them. CI validates their structure on every push; a malformed
file fails the check before it can reach devices.

## Caveats that will bite

- **Renaming this repository changes the Pages URL.** `mish5000.github.io/<name>/`
  follows the repository name and GitHub does **not** redirect the old Pages path.
  Every installed home-screen icon points at the current URL and would break. If
  the repository is ever renamed, plan a custom domain first and migrate the
  installs onto it.
- **Making this repository private disables Pages** on the free tier, which takes
  the live site down.
- **The service worker caches aggressively by design.** When testing a change,
  a hard reload is not always sufficient — unregister the worker in Safari's
  Web Inspector, or send it `flush`.
